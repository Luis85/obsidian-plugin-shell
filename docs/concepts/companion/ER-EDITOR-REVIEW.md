# Entity editor: research, product review and polishing

Reviewed 2026-09-24 against PR #5 head `cf516b0062f7a44d2b31f27e95fefbf15fd73d3f`. This record concerns the offline companion concept, not an installed native editor. Read [the execution record](ER-EDITOR-VERIFICATION.md) for actual evidence and remaining qualification.

## Outcome and product direction

**Build the semantic layer quickly without needing to think like a database administrator.** The user is designing the plugin's entities, note properties and relationships inside one authoring vault. They are not editing live records or configuring SQL foreign keys. Retain the existing entity/property/relationship contract and the common sitemap interaction language. Repair correctness first, reduce repeated entry next, and make arrangements and relation meaning understandable without relying on dragging or notation alone.

The task sequence is: add a thing the plugin manages; define its properties; connect it to another entity; read the relationship in both directions; group and arrange the diagram; review the generated contracts. A model is useful when the author can explain both the stored representation and the application behavior still needed. A beautiful line is not evidence of enforced referential integrity.

## Research and decisions

Primary documentation was reviewed across modeling tools, the actual rendering engine, native Obsidian storage and accessibility. These are design inputs, not a claim of user interviews, comparative usability testing or a full accessibility audit. Retrieved on 2026-09-24. ### Why not a full database-modeling workbench?

SQL indexes, normalization assistants, DDL import, inferred join tables and an unlimited graph would add concepts not justified by Obsidian notes. This pass instead improves the existing semantic model and its preview output. Automatic layout is a convenience, not permission to change schema. A relationship remains stored once on its source entity; inverse queries, missing/ambiguous links, note renames, enforcement and migration still need native application services.

## Reproduced connector defect

The original selector `.er-flow .vue-flow__edges svg` addressed a descendant SVG. In the embedded runtime, the edge layer is itself `svg.vue-flow__edges`. The actual inner SVG still computed to `overflow: hidden`, so a perfectly valid path could disappear at the viewport-sized SVG boundary after large world-coordinate translations. Checking that a path existed would not detect this failure.

The correction targets `#er-flow svg.vue-flow__edges` and the connection preview SVG, leaving `#er-flow` itself clipped. Endpoint positions come from the actual identified handles. Ports face toward the other card; stacked and recursive layouts have suitable alternatives. Routing scores bounded orthogonal candidates against entity rectangles, favors unobstructed paths and renders rounded corners. The full relationship name and meaning remain in the inspector/title when a short diagram caption is truncated.

The new regression test moves the whole model to large positive/negative coordinates, samples actual rendered SVG points with `elementFromPoint`, and measures endpoint/handle distances in screen space. Temporarily reintroducing the old clipping rule must make that same hit-test probe fail; removing it restores the lines. This is stronger evidence than a screenshot or a nonzero SVG path length alone.

Routing is not a global optimizer. Overlapping cards and dense graphs can still produce crossings or occlusions; the selected candidate exposes `data-obstructed` for diagnostics. Move cards with guides or use Position / align. There is no claim of universally crossing-free paths, collision-free labels or a shortest possible diagram.

## Interaction contract

Hovering an entity emphasizes its border and reveals optional connection ports. Selecting it adds the persistent selection ring and updates the catalog/inspector. Keyboard focus adds a distinct dashed outline. Source ports are filled/square; targets are hollow/round. Connected secondary ports remain visible even without hover so a line cannot appear to terminate in empty space. A valid target receives a contrasting ring and fill during connection dragging. Hovering or selecting a relationship highlights its endpoints and source-owned field. Leaving hover restores the selected relationship, if any.

Guidelines and Grid snap are separate persisted presentation preferences. They do not invalidate a source plan. A drag records one history snapshot at successful drop. Escape keeps the old arrangement. Arrow keys move the focused entity one unit, Shift+arrow twenty; Ctrl/Cmd+Z undoes and Shift+Ctrl/Cmd+Z redoes. Enter opens the focused entity or relation editor. F fits measured nodes. Inputs, textareas, selects and editable content keep their own keys. The numeric Position / align draft uses left/top edges or horizontal/vertical centers relative to a selected reference entity.

Disabled editing controls are visibly unavailable during a simulation and their underlying operations remain guarded. Read-only inspection, schema previews and navigation remain usable. Error states retain drafts and focus the error message. Empty states offer a first entity or an explicitly optional example. No example is injected into an existing model.

## Acceptance and follow-on work

The current suite verifies rendering and endpoint attachment, real pointer gestures, visual-state styles, canonical state/history, unchanged generator bytes and lifecycle cleanup. Existing semantic, singleton, component-variant, sitemap, recovery and storage suites are run on the same generated artifact. [Verification details](ER-EDITOR-VERIFICATION.md) distinguish executed local evidence from GitHub integration.

Native keyboard/screen-reader testing in Obsidian, physical touch/device testing, formal WCAG contrast/target-size conformance, high-density graph benchmarking, sophisticated label collision routing, nested/collapsible sections, row-specific ports, multi-selection distribution and relationship endpoint-updater dragging remain follow-on work. The current bounds of 60 entities, 40 authored properties, 160 relationships and 16 sections are validation guardrails, not performance promises.
