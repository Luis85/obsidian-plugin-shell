## Reviewed observation boundary

`LifecycleObservations` emits immutable metadata after an actual notice, modal,
timer or recovery registry is acquired. A matching release follows successful
handle cleanup, natural timer completion or action settlement. Failed dismissal,
close or cancellation leaves the resource outstanding in independent evidence;
a caught cleanup error cannot manufacture a zero-resource result.

Recovery registry capability and pending availability are separate resources.
Removing a registry immediately prevents invocation, but it cannot cancel an
arbitrary promise returned by `available()`. That pending observation remains
until settlement; a successful late result cannot run a removed action. A late
availability rejection produces its own exact `notice.action` fault.

Observers receive only safe owner/operation tokens, numeric identity/count and
resource phases. They receive no notice handle, timer cancellation, action,
publisher, service or mutation method. The runtime exposes subscription and
counters through `runtime.observation`; publication stays inside composition.
No production globals, private host managers or global resource sweeps are added.

The driver attaches a separate JSHandle ledger before its scenario. It verifies
zero prior caught errors and observer failures, consecutive event sequences,
agreement with total runtime error/resource counters, exact fault codes/counts,
zero lost records and zero observer failures. The ledger cap of 4,096 fails
explicitly rather than silently truncating; it is independent of the 200-entry
production diagnostic display. The Items controlled-adapter scenario asserts
exactly one `settings.write` / `settings.save` fault before reconstruction.

The trusted native producer validates those serialized ledgers through
`native-resource-report.mjs`, including actual sequence continuity, exact fault
counts, matching resource releases and unchanged checkpoint prefixes. Its legacy
`itemOwnership.diagnostics` field is derived from independent error events and
marked `diagnosticSource: independent-runtime-observer`; it no longer reads the
production ring. New claims require the new independent packets, while historical
fixture-only reports keep their earlier parsing scope.

## Bounded native experiment

Prerequisites: fresh isolated contained vault/configuration, explicitly provisioned
host, current resource availability, frozen source and exact installed asset
hashes. Parent serializes the launch. No retained candidate is instrumented or
rewritten. Preserve the first result, screenshot, independent ledger, receipts,
primary errors and cleanup errors. Stop on a reproduced failure for analysis.

1. Subscribe to the installed runtime, then invoke the separately installed
   qualification fixture's command to create a persistent native `Notice` through
   the public API. That plugin owns the Notice; the driver retains its DOM element.
2. Open two actual showcase leaves. In one renderer turn, dispatch the real
   optional recovery-example button and close its owning leaf. Require the real
   300 ms progress timer to acquire/release without a progress sink appearing.
   Open a fresh initiating leaf beside the retained sibling for the next phase.
3. Both leaves create ordinary native notices. Start the initiating view's
   modal-backed recovery example. Retain the actual native action function in a
   named public-CDP object group using `DOMDebugger.getEventListeners`, then invoke
   it twice with `Runtime.callFunctionOn`. The real modal remains unresolved:
   require one pending availability check, one registry and the disabled action. Wait
   for the genuine 300 ms delayed progress notice to appear.
4. Close only the initiating leaf. Require its notices/modal/timers/registry to
   release and pending availability to settle without success. Invoke the retained
   native action function again after close; require unchanged ledger sequence and
   no UI resurrection. Removing DOM listeners therefore cannot hide a missing
   guard. The sibling's ordinary notice/timer remains, its real event action works,
   and the unrelated persistent native Notice remains usable.
5. Disable the plugin. Require all observed plugin resources to release, both
   retained plugin notice elements to remain detached and the independent fault
   ledger to remain exactly empty. Update the foreign Notice successfully through
   its fixture command, then disable the fixture plugin and verify its owned
   Notice element is detached. The driver does not obtain the Notice instance.
6. Restore the enabled plugin and view for the remaining native protocol. Retain
   observation and cleanup failures separately from the primary failure.

The ordinary native notice lifetime remains the real six-second policy bound.
Split preparation occurs before notice creation; if later modal/close interaction
is too slow and natural expiry intervenes, preserve the failed ownership assertion.
Do not extend the lifetime or retry the experiment to manufacture surviving handles.

The initial pre-demo audit found no production UI caller for delayed progress or

The enhanced native packet requires atomic progress cancellation, pending recovery,
retained function replay and final resource cleanup. Component doubles, the served

claims native execution. Frozen-candidate native execution is still required.

## Independent controls and retained uncertainty

`independent-fault-observation.test.ts` exercises 205 actual caught recovery
failures, comparing the complete independent ledger with the truncated display.
`lifecycle-observation.test.ts` asserts individual resource lifetimes, sibling
preservation, cancelled timer callbacks, pending availability, exact cleanup
faults, observer failures, synchronous timer completion and overflow handles.
`native-runtime-observation.checks.mjs` proves the actual native ledger validator
rejects lost delivery, unexpected faults, subscriber failures, orphan releases
and capacity overflow. These remain unit/tooling evidence until their own trusted
producer output is observed; none is a substitute for running the native driver.

The independent review reproduced reentrant observer defects before correction:
acquisition callbacks could close owners before handle registration, overflow and
legacy replacement could strand a handle, old registry release could erase a
successor, and transient updates could acquire another resource after closure.
The retained `c-reentrancy-red.log`, `c-reentrancy-red-extended.log` and
`c-reentrancy-transient-red.log` distinguish those failures. Corrections recheck
the exact current entry/request, release superseded handles, register cleanup
before publishing old-owner release, and retain failed cleanup as outstanding.
The `lifecycle-observer-reentrancy.test.ts` controls include successor preservation
and exact adapter call counts; a balanced receipt list alone cannot hide an
unnecessary late resource acquisition. Rejected asynchronous observers produce
independent faults rather than unhandled rejections.

Scope is notification-policy timers and registered native sink handles. The
observer does not claim a global native timer census or measurement of unrelated
host event-bridge scheduling. The resource experiment asserts the baseline of
resources acquired after its attachment and records that attachment sequence.
