# CX-001 — Maintain the evolving concept feature inventory

## Outcome
Concept development remains open and traceable without competing with the shell's highest-priority implementation work.

## Baseline and scope
Inspect the latest [concept guide](../../concepts/companion/README.md), source, reviews, [current PRD](../../product/COMPANION-PLUGIN-PRD.md) and requested test-data/design-system capabilities. Separate implemented-in-concept, proposed, revised and deferred behavior from native implementation status.

## Acceptance criteria
- [ ] Every selected feature has intent, observable behavior, unresolved questions and a shell dependency mapping.
- [ ] Requirements, sitemap, entities, components, sources, actions, fixtures and design-system work remain accounted for; no feature-complete claim is introduced.
- [ ] Newly discovered generic requirements create or refine SH tasks before native adoption; product-specific UI remains in concept/companion lanes.
- [ ] Scope decisions preserve history and explicit deferrals instead of silently removing inconvenient features.

## Verification
Walk the inventory against current screens, contracts and user requests. Confirm that simulated capabilities remain simulated and that native status cannot be promoted by concept test results.

## Evidence and handoff
Not executed. Record inspected concept revision, feature matrix and decisions. Subsequent CX tasks may continue secondarily while P0 shell work proceeds.
