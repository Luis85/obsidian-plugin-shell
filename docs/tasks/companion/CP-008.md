# CP-008 — Integrate development, verification and recovery

## Outcome
Developers can understand and control supported project operations through real evidence, with safe recovery from failures.

## Baseline and scope
Consume the shared operation catalog/protocol, error services, ownership receipts and qualified execution boundary. Retain the first-class user-run CLI path and do not introduce arbitrary shell-command forms or another process manager.

## Acceptance criteria
- [ ] Development and quality entries reflect delivered capabilities; source/build/install/native scopes and evidence freshness are individually visible.
- [ ] Failed, stale, cancelled, skipped and unexecuted checks cannot appear as passed merely because a process exited or a screen advanced.
- [ ] Multiple leaves share one project-operation owner, bounded redacted logs and durable receipts while retaining per-view drafts.
- [ ] Cancellation, unload and late completions respect shell ownership; recovery explains known writes and preserves subsequent external edits.
- [ ] Uncertain outcomes require inspection, not blind retry; no universal rollback or sandbox claim is made.

## Verification
Exercise concurrent leaves/CLI operations, failed checks, stale receipts, long output, cancellation, restart and partial generation. Confirm actual process/write evidence and independent diagnostic-error observation.

## Evidence and handoff
Not executed. Record operation versions, real failure/recovery receipts and platform-specific limits. Releasing, enabling code and changing host security settings remain separate deliberate actions.
