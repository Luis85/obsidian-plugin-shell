# SH-002 — Establish reusable product composition

## Outcome
Two differently identified plugins compose the same maintained shell through public extension points without a companion dependency.

## Baseline and scope
Inspect [feature authoring](../../development/BUILD-A-FEATURE.md), `src/features/api.ts`, bootstrap registries and the [companion-on-shell contract](../../architecture/COMPANION-ON-SHELL.md). Extend demonstrated API gaps; do not fork the foundation or require a large package migration without evidence.

## Acceptance criteria
- [ ] A minimal consumer and a distinct richer reference consumer register features, services, commands and views through explicit composition.
- [ ] Identity-derived settings, view, command and CSS namespaces do not collide; no public manifest identity is changed as a planning shortcut.
- [ ] Neither consumer requires changes to generic persistence services or main.ts for business-specific behavior.
- [ ] Shell domain/application imports remain framework-free; companion dependencies are rejected by architecture tests.

## Verification
Compile both compositions, exercise real shared services, and add negative dependency/identity fixtures. Preserve current code-line, coverage and analyzer gates. Document the small supported API and compatibility policy.

## Evidence and handoff
Not executed. Record both consumer identities, foundation revision, actual test results and any unqualified host behavior. The companion itself is implemented later in CP-001.
