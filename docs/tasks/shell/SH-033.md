# SH-033 — Qualify the framework-side companion operation adapter

## Outcome
The framework exposes everything the future companion needs through shared typed contracts without needing the native companion to exist first.

## Baseline and scope
Build a headless reference consumer of discovery, validate/import, generation plans, execution, progress/results, diagnostics, recovery, source/fixture and design-token operations. Use data-only metadata and shared services. Direct in-plugin process execution or rich live RPC remains separately capability/policy gated.

## Acceptance criteria
- [ ] A non-UI consumer and CLI submit the same typed inputs and receive equivalent supported plans/results; neither parses human terminal output nor runs a private compiler.
- [ ] Schema/protocol/template compatibility and availability prevent the UI advertising missing behavior; portable documents never grant trust or carry receipts as authority.
- [ ] Request IDs, cancellation, stale approvals, lock contention, failure/uncertainty and bounded progress are testable; results invalidate when source/config/plan identity changes.
- [ ] Actual headless filesystem effects and preservation match CLI behavior; source adapters/test-data/token exports have no browser-global or companion dependency.
- [ ] User-run CLI handoff works when native execution is unavailable or policy is unresolved; no production arbitrary-eval bridge is required to ship the kit.
- [ ] CP-004/CP-008 receive a documented adapter contract and remaining native-only acceptance list; this test consumer is not CP-001 conversion.

## Verification
Run contract conformance across CLI/headless adapters with real bounded file plans and fault injection. Keep actual Obsidian/native lifecycle qualification in later CP tasks.
