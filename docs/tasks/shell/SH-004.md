# SH-004 — Complete generic durable entity persistence

## Outcome
Consumer-defined records, including future design records, persist safely without Task-specific or companion-specific service branches.

## Baseline and scope
Reuse [DocumentCreationService](../../architecture/DOCUMENT-CREATION.md), entity repositories and [plugin-data semantics](../../development/PLUGIN-DATA-ENTITIES.md). Assess custom fields, stable IDs, schema versions, references and owned structured payloads. Do not introduce an ORM or duplicate editable database.

## Acceptance criteria
- [ ] A distinct consumer schema persists every supported field, including false, zero, dates, lists and explicit defaults; unsupported shapes fail visibly.
- [ ] Updates preserve note identity/path, creation metadata, handwritten body and unrelated properties; title-based creation retains existing collision rules.
- [ ] Stale revisions, corrupt/future data, duplicate identities and uncertain writes retain recoverable data and never trigger blind retry.
- [ ] Plugin-data consumers continue using the one shared writer; note-backed entities remain Markdown-canonical.

## Verification
Assert exact bytes, round-trip and migration behavior, external-edit conflicts, duplicate submission handling and real committed events. Exercise a second non-Task schema and native processing separately from mocks. No cross-process atomicity claim without evidence.

## Evidence and handoff
Not executed. Link schema/API changes, fixture bytes and actual tests. Record partial or unsupported mapping cases for generators and companion records.
