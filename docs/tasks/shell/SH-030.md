# SH-030 — Provide ownership-aware maintenance and upgrades

## Outcome
The CLI remains the maintenance interface after generation and publication without overwriting developer-owned code.

## Baseline and scope
Implement framework status/doctor, compatibility inspection and reviewed upgrade/regeneration/migration plans. Keep framework-owned modules, developer source and regenerable artifacts distinct; preserve the project-pinned version.

## Acceptance criteria
- [ ] No global/latest tool silently replaces the pinned framework; incompatible schema/template/runtime combinations fail with an actionable report.
- [ ] Upgrade, reimport, regeneration, source-folder relocation and runtime-data migration remain separate reviewed operations.
- [ ] Ownership/preimage/version binding preserves edited/foreign files; no-op reruns write nothing; stale approvals and concurrent changes fail safely.
- [ ] Recovery truthfully reports committed/uncertain/preserved states; it never rewrites live plugin settings behind the shared writer.
- [ ] Compatibility aliases have explicit deprecation/migration policy and generation manifests do not replace the dependency lockfile.

## Verification
Exercise an old qualified consumer upgraded to a new fixture version, customized source before/after preview, corrupted ownership records, wrong global versions and interrupted migration recovery.
