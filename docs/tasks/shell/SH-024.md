# SH-024 — Extract the shared TypeScript tooling core

## Outcome
CLI, project compiler and future companion use one typed implementation of capabilities instead of parallel command scripts.

## Baseline and scope
Follow the [CLI/generator plan](../../development/FRAMEWORK-CLI-GENERATOR-PLAN.md). Incrementally extract existing makers, file plans, validation, source/fixture/token contracts and diagnostics behind framework-free ports. Preserve the public feature API; logical modules precede optional workspace packaging.

## Acceptance criteria
- [ ] Authored capability/business logic is TypeScript with explicit schemas and typed requests/results; compatibility launchers contain no duplicate implementation.
- [ ] Domain/application/shared semantic contracts have no Node, Obsidian, Vue, Pinia, terminal or browser imports; concrete adapters own I/O.
- [ ] Individual makers and full project generation consume the same services; shared runtime behavior is imported rather than copied into each feature.
- [ ] Behavioral parity preserves legacy guards, statuses, ownership/recovery and exact-byte transfer; discovery never evaluates custom code.
- [ ] Type/build/analyzer/coverage boundaries include all new shared inputs without weakening current limits; runtime bundles exclude CLI dependencies.

## Verification
Run differential legacy/new entry tests, import-graph and bundle inventories, typed consumer compilation, malformed input and independent headless adapter tests.

Not executed. Record exact commits/artifacts, commands/results, environment and remaining scope. Documentation is not implementation evidence or execution authorization.
