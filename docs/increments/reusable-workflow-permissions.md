# Guard reusable-workflow calls against permission escalation

<!-- Developer handoff for one pull request. `npm run dor` checks it before implementation,
`npm run dod` after it. Replace every <placeholder>; delete these comments when done. -->

## Summary

The first Release tier run on `release/0.5.0` ended in `startup_failure` with no jobs: ci.yml's `ci-result` job requests `checks: read`, but release.yml, which calls ci.yml as a reusable workflow, granted only `contents: read`, and GitHub rejects a run when a called workflow's job requests more than its caller grants. Neither `npm run check:repository` nor the workflow model checks caught it. A new guard test compares, for every job that calls a local reusable workflow, the caller's grant with every permission the callee and its jobs request; release.yml carries the same `checks: read` fix as `release/0.5.0`.

## Outcome

A workflow change that makes a local reusable-workflow call request more permissions than its caller grants fails the quality suite before it can fail a Release tier run at startup.

## Scope

### In scope

- A test in `tooling/tests/interactive-maker-ci-workflow-model.checks.mjs`: every job in `.github/workflows` that calls `./.github/workflows/<file>` declares a grant (its own `permissions` or its workflow's), and no callee top-level or job permission exceeds it (none < read < write; `read-all`/`write-all` expand to every scope).
- In-memory negative cases: release.yml granting only `contents: read` reports ci-result's `checks: read`; a job-level grant replaces the workflow grant.
- release.yml's top-level `checks: read`, identical to the fix on `release/0.5.0`, so the guard passes on `main` before 0.5.0 is published.

### Out of scope

- Moving the rule into `npm run check:repository`.
- Nested reusable-workflow chains (none exist); a callee that calls another workflow without its own grant fails the explicit-grant assertion instead of being followed.
