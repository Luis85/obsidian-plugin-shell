# Release cut runs without an environment approval; Publish keeps it

<!-- Developer handoff for one pull request. `npm run dor` checks it before implementation,
`npm run dod` after it. Replace every <placeholder>; delete these comments when done. -->

## Summary

Every release needed two `release` environment approvals: one for Release cut and one for Publish. The cut only creates a release branch and a draft pull request and publishes nothing, so it moves to its own `release-cut` environment without reviewers; Publish keeps the reviewer-protected `release` environment. The repository workflow guard pins each allowlisted file to its environment.

## Outcome

A maintainer dispatches Release cut and it runs without waiting for an approval; the single reviewer approval of a release is the one on Publish.

## Scope

### In scope

- `tooling/quality/workflow-policy.mjs`: a per-file environment for write jobs (`release-cut.yml` → `release-cut`; `publish.yml` and `obsidian-release.yml` → `release`), and `release-cut.yml` targets `release-cut`.
- Guard tests, the release guides, the workflow reference and the release skill.

### Out of scope

- Publish, its reviewers and the generated projects' release workflow: they keep the `release` environment.
- Repository settings (environment secrets, reviewers): owner steps listed in the guide.
- The `action_required` pull-request runs on release pull requests, which workflow configuration cannot prevent; the guide documents that they can be ignored.

## Risks and rollback

Risk: anyone with write access can cut a release branch without review; it publishes nothing and Publish still needs the reviewers. If `RELEASE_TOKEN` is an environment secret of `release`, the cut falls back to `GITHUB_TOKEN` until it is added to `release-cut`. Rollback: revert the commit.

## Dependencies

None in code. Owner settings: optionally add `RELEASE_TOKEN` to the `release-cut` environment.
