# `scripts/` consolidation plan

Status: Stages A–D complete; Stage E complete on PR #67, including the companion code emitters' move to `bin/compiler/emitters` (E4 below); the starter domain moved to `bin/adapters/starters` (M3 below); the last runtime modules left `scripts/` and no `bin` ↔ `scripts` two-way folder pair remains (M4 below). Stage F moved the generated-project templates to `templates/` (see F1 below). The continuation uses separately pushed
milestones on the same PR; each validation checkpoint is expected to pass the repository's existing
gates before deeper restructuring, with no threshold or scope exemptions. The inventory and sequencing below are planning inputs,
not permission to weaken any quality gate.

## Target shape

| Location | Owns | Quality gates |
| --- | --- | --- |
| `src/` | Obsidian plugin runtime only. | Production coverage/complexity; no Node, CLI or `scripts/` imports. |
| `bin/` | The developer CLI application in TypeScript: `app.ts` entry, commands, domain/application/adapters/presentation, the compiler (`bin/compiler`, including the companion code emitters in `bin/compiler/emitters`), the docs package (`bin/documentation`), the maker engine, recipes and recipe catalog data (`bin/adapters/makers`), the starter domain (`bin/adapters/starters`), the capability catalog and its operation data (`bin/adapters/operations`), and the release bundler, prototype-skill reader and companion-project reader (`bin/adapters/framework`). | Production view: `tsconfig.maker.json`, ESLint + oxlint, maker coverage (90/90/90/85; 95/95/95/90 for `bin/{domain,application}`, `bin/compiler/{domain,application}` and `bin/documentation/{domain,application}`), complexity 10/15, duplication 3%. |
| `scripts/` | Real scripts: gates, suite runners, build/dev loop, release and qualification entry points invoked by npm scripts or workflows (the companion tools in `scripts/companion-tools`), plus three justified non-tooling holdings (M4 audit below): the shared typed contracts (`scripts/{contracts,shared}`), the starter schema data (`starters/starter.schema.json`) and the companion contract library (`scripts/companion`, exactly the `companion-authoring-contract` zone). | Tooling view; the contract zones are typed and boundary-checked. |
| `templates/` | Generated-project template sources (Stage F): `companion/runtime` (runtime modules copied or rewritten into generated projects, plus the journey vault adapter their native code imports in place), `companion/devkit` (developer-kit `.tmpl` text) and `examples` (example-removal templates). The template snapshot and the kit copy it like the other framework roots. | Templates view (diagnostic, measured as its source language), Fallow zone `project-templates` (may import only itself and `companion-authoring-contract`), 400 code lines per file. |

**Nothing moves into `src/`.** No `scripts/` module is plugin runtime logic, and `src/` never imports
`scripts/` or `harness/` today. "Incorporate into TypeScript" therefore means the CLI's own layered
source under `bin/`.

- The typed Markdown documentation package lives in `bin/documentation` (E5b); its settings adapter and the maker settings share the neutral project-path policy.

Inside `bin/`, `bin/adapters/framework` ↔ `bin/adapters/starters` stays a folder-level pair without a file-level cycle (justified in the M4 audit).
- Compatibility `.mjs` entries for JSON data, process, input, confirmation, hash, project-path, bounded mapping and file plans delegate to typed core modules. The maker engine is strict TypeScript (E6b, E6c); remaining untyped code is real tooling scripts and the companion `.mjs` contracts.
