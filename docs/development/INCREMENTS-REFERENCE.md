# Increments reference

> Type: reference · Part of the [docs index](../README.md)

Facts about the documents, statuses, branches, files and results of the
`node bin/app increment`, `pr` and `issue` commands. The documents are Markdown
files in the repository and they are the source of truth; the CLI edits them
through reviewed plans and reads the hosting platform only for `pr publish` and
`pr sync`. Exact command syntax is in the generated
[command reference](../user-manual/shell-cli/generated/reference.md); the rules that
check the documents are in [Definition of Ready and Done](DEFINITION-OF-READY-AND-DONE.md).

## Documents and folders

| Document | Folder (setting, default) | File | Holds |
| --- | --- | --- | --- |
| Increment | `paths.increments`, `docs/increments` | `<id>.md` | One deliverable outcome: the developer handoff the Definition of Ready and Done check. |
| PullRequest | `paths.pullRequests`, `docs/pull-requests` | `<id>.md` | One planned pull request of an increment: kind, branches, tasks, documents, amendments, and after publication its binding to the hosting platform. |
| Issue | `paths.issues`, `docs/issues` | `<id>.md` | One trackable part of an increment with its own criteria; local only. |
| Sync record | `.workbench/pull-requests` | `<pr-id>.sync.json` | The machine-owned base of the last publish or sync; commit it with the document. |
| Acceptance stub | `acceptance.pattern` in `delivery.json` | `tests/acceptance/<increment>/ac-<n>.checks.mjs` | One pending test per acceptance criterion. |

The `paths` keys live in `configs/user-settings.json`. They are optional and
default as shown; `node bin/app settings migrate --input <paths.json>` moves the
folders and rewrites `handoff.glob`, `pullRequests.glob` and `issues.glob` of
`configs/delivery/delivery.json` in the same reviewed plan. When the globs and the
settings disagree, read commands warn and write commands refuse with
`DELIVERY_PATHS_DRIFT`. A `README.md` in a folder, and anything in the configured
`ignore` lists, is not a document. Ids are slugs (`^[a-z0-9]+(?:-[a-z0-9]+)*$`,
at most 64 characters) and equal the file name.

Without `configs/delivery/delivery.json` the CLI uses built-in defaults equal to
the shipped file, and the Definition of Ready falls back to a structural check.

## Increment document

```markdown
---
type: Increment
id: export-notes
title: "Export notes as JSON"
owner: "Luis"
size: M
status: New
e2e: optional
refs: ["[[docs/prds/export]]"]
pullRequests: [export-notes-kickoff, export-notes-1]
issues: [export-notes]
branch: "increment/export-notes"
base: main
---
```

| Key | Required | Values |
| --- | --- | --- |
| `type` | yes | `Increment` |
| `id` | yes | slug, equal to the file name |
| `title` | yes | one line, at most 120 characters |
| `owner` | yes | a name or handle (may be empty while New) |
| `size` | yes | `S`, `M` or `L`; sets the criteria and affected-area budgets (DOR-12) |
| `status` | yes | see [Statuses](#statuses-and-transitions) |
| `e2e` | yes | `none`, `optional` or `required`; `required` needs the `e2e` pull request label (DOD-10) |
| `refs` | no | paths, `[[wikilinks]]`, requirement ids or `#123`/https references |
| `pullRequests`, `issues` | no | ids of the PullRequest and Issue documents of this increment; the CLI keeps them in sync |
| `branch`, `base` | no | the increment branch and its base |

Sections, in this order: `Summary`, `Outcome`, `Scope` (with `### In scope` and
`### Out of scope`), `Acceptance criteria` (`- [ ] AC-n: text Evidence: \`path\``),
`Affected areas`, `Test plan`, `Docs impact`, `Changelog`, `Risks and rollback`,
`Dependencies`, `Open questions`. Two CLI-owned sections follow, each between
markers that are rewritten on every change (edits inside are replaced):

```markdown
## Issues

<!-- wb:issues generated by node bin/app; edits here are replaced -->
- [[docs/issues/export-notes|Export notes as JSON]] · New
<!-- /wb:issues -->

## Pull requests

<!-- wb:pull-requests generated by node bin/app; edits here are replaced -->
- [[docs/pull-requests/export-notes-kickoff|Kick-off: Export notes as JSON]] · Draft · [#12](https://github.com/o/r/pull/12)
<!-- /wb:pull-requests -->
```

`## Completion record` is generated by the Definition of Done (`--write` or
`increment complete`); regenerate it instead of editing it. The body is rendered
from `configs/delivery/increment-handoff.template.md` when it exists.

## PullRequest document

```markdown
---
type: PullRequest
id: export-notes-1
title: "Export command"
kind: change
increment: export-notes
status: Draft
delivers: [AC-1, AC-2]
head: "pr/export-notes/export-notes-1"
base: increment/export-notes
platform: github
repository: "o/r"
number: 13
url: "https://github.com/o/r/pull/13"
publishedAt: 2026-10-04T12:00:00Z
lastSyncedAt: 2026-10-05T08:00:00Z
---
```

| Key | Required | Values |
| --- | --- | --- |
| `type`, `id`, `title`, `status`, `increment`, `head`, `base` | yes | `PullRequest`; slug; one line; see statuses; the Increment id; branch names |
| `kind` | no | `kickoff` (one per increment, created by `increment new`) or `change` (default for `pr new`) |
| `delivers` | no | acceptance criteria of the Increment this pull request completes; a change pull request's Definition of Done checks only these |
| `issues` | no | Issue ids this pull request resolves (`pr issue add`) |
| `platform`, `repository`, `number`, `url`, `publishedAt`, `lastSyncedAt` | no | the binding, written by `pr publish` and `pr sync` only |

Sections: `Summary`, `Scope` (`### In scope`, `### Out of scope`), `Tasks`
(`- [ ] T-n: text`), `Documents` (`- [[path|label]]`), `Notes` and `Amendments`
(`### A-n · YYYY-MM-DD` entries, appended after publication). A change pull
request's Definition of Done adds its own `## Completion record`.

Default ids: the kick-off is `<increment>-kickoff`, change pull requests are
`<increment>-<n>`, issues `<increment>` then `<increment>-<n>`. Item ids (`AC-n`,
`T-n`, `A-n`, `IC-n`) are never reused; they are the keys of the sync.

## Issue document

Frontmatter `type: Issue`, `id`, `title`, `status`, `increment` and optional
`pullRequests`. Sections `Summary`, `Acceptance criteria` (references to the
Increment's `AC-n` or the issue's own `IC-n`) and `Notes`. Issues are local
documents; nothing syncs them to GitHub Issues or Azure Boards.

## Statuses and transitions

Statuses accept the exact name or a slug (`in-progress`).

**Increment** (`increment status <id> <status>`):

| From | To | Guard |
| --- | --- | --- |
| New | Refining, Ready, Cancelled | Ready: the Definition of Ready without DOR-01 and DOR-15 (`INCREMENT_NOT_READY`) |
| Refining | Ready, Cancelled | as above |
| Ready | Refining, In progress, Cancelled | `pr publish` moves a Ready increment to In progress in the same plan |
| In progress | Refining, Done, Cancelled | Done: every pull request of the increment Merged or Closed and at least one Merged (`INCREMENT_OPEN_PULL_REQUESTS`) |
| Done | none | terminal |
| Cancelled | Refining | Cancelled needs no Draft or Ready pull request |

**PullRequest:** `New` (planned) → `Draft` (published by `pr publish`) → `Ready`
(marked ready on the platform) → `Merged`, or `Closed`. Locally only an
unpublished pull request moves between New and Closed (`pr status`); Draft, Ready,
Merged and a remote Closed come from `pr sync`, which also accepts a remote
reopen. The CLI never marks a draft ready and never merges.

**Issue** (`issue status`): New → Ready, In progress, Cancelled; Ready → New,
In progress, Cancelled; In progress → Ready, Done, Cancelled; Done → In progress;
Cancelled → New. Done needs every issue criterion ticked.

## Edit locks

| Document state | Allowed edits | Refusal |
| --- | --- | --- |
| Increment New, Refining, Ready, In progress | every content edit | |
| Increment Done or Cancelled | none (reopen Cancelled → Refining first) | `INCREMENT_LOCKED` |
| PullRequest New (unpublished) | title, branches, sections, scope, documents, notes, tasks, attach, issue links | `pr amend`: `PR_NOT_PUBLISHED` |
| PullRequest Draft or Ready (published) | `pr task add`, `pr task set`, `pr amend` | `PR_LOCKED` |
| PullRequest Merged or Closed | none | `PR_TERMINAL` |
| Issue Done or Cancelled | none (reopen through its status) | `ISSUE_LOCKED` |

## Branches

From `branches` in `delivery.json`:

| Pattern | Default | Created by | Start point |
| --- | --- | --- | --- |
| `branches.base` | `main` | | |
| `branches.increment` | `increment/{id}` | `increment new` (head of the kick-off) | `origin/main` when present, else `main` |
| `branches.pullRequest` | `pr/{increment}/{pr}` | `pr new` (head of a change pull request) | the local increment branch, else `origin/increment/{id}`; `--fetch` updates it first |

A change pull request has base `increment/{id}`, so it stacks on the increment's
latest state; `pr new` refuses another base unless `--base` is given explicitly
(with a warning). Branch creation is a reviewed `git-branch` step of the plan: its
name, start ref and start commit are part of the plan hash. `--branch` and
`--no-branch` choose (the default creates it when git is available and the branch
does not exist), `--switch` checks it out, `--fetch` fetches the start branch
first; nothing is fetched otherwise. Only `pr publish` pushes, and only a head
branch that is missing on the remote, on apply (`--no-push` refuses instead with
`PR_HEAD_NOT_PUSHED`).

## Published pull request body

`pr publish` renders a managed block into the pull request description; text
outside it (reviewer notes, platform templates) is kept byte for byte and never
imported.

```markdown
<!-- wb:pr v1 id=export-notes-1 increment=export-notes kind=change -->
Handoff: docs/increments/export-notes.md
…regions wb:summary, wb:scope, wb:acceptance, wb:tasks, wb:documents, wb:notes, wb:amendments…
<!-- /wb:pr -->
```

| Region | Class | On sync |
| --- | --- | --- |
| header, `acceptance` | derived | Always re-rendered from the local documents; remote edits are discarded with `PR_REMOTE_DERIVED_EDIT_DISCARDED`. |
| `summary`, `scope`, `documents`, `notes`, title | frozen after publication | A remote edit is pulled; a local hand edit conflicts (`PR_LOCKED_REGION_EDITED`; record the change with `pr amend`). |
| `tasks`, `amendments` | mutable | Three-way merge by id: ticks never conflict, text changed on both sides does; tasks or amendments added on the platform without an id are imported with the next id. |

Wikilinks are published as links to the file on the head branch (GitHub blob
URLs, Azure `?path=…&version=GB<head>`) and converted back on sync. Where a
platform drops HTML comments, the markers can be written as Markdown reference
definitions (`[//]: # (wb:summary)`); parsing accepts both.

Limits: title 120 characters; body 65,536 characters on GitHub and 4,000 on Azure
DevOps (`PR_BODY_TOO_LARGE`, never truncated); 200 tasks, 100 amendments,
100 documents (`PR_LIMIT`); notes 20,000 and one amendment 10,000 characters.

## Sync record

`.workbench/pull-requests/<pr-id>.sync.json`, written by `pr publish` and every
applied `pr sync`, committed next to the document:

```json
{
  "schemaVersion": 1, "id": "export-notes-1", "platform": "github", "repository": "o/r", "number": 13,
  "remoteRevision": "<sha256>", "bodySha256": "<sha256>", "derived": "<sha256>", "title": "<sha256>",
  "regions": { "summary": "<sha256>", "scope": "<sha256>", "documents": "<sha256>", "notes": "<sha256>" },
  "tasks": { "T-1": { "text": "<sha256>", "checked": false } }, "taskOrder": ["T-1"],
  "amendments": { "A-1": "<sha256>" }, "state": "Draft", "head": "pr/export-notes/export-notes-1",
  "base": "increment/export-notes", "syncedAt": "2026-10-05T08:00:00Z"
}
```

It holds hashes of normalized text only (LF line ends, trimmed line ends,
wikilinks in resolved form), enough to tell which side changed. A missing record
fails `pr sync` with `PR_SYNC_RECORD_INVALID`.

## Effects and exit codes

| Effect | Commands | Behaviour |
| --- | --- | --- |
| read | `list`, `show`, `validate`, `increment check`, `pr show` | Reads local files only; `pr show` never contacts the platform. |
| plan | every other `increment`, `pr` and `issue` command | Previews a file plan (and the branch step); writes only with `--yes` or `--apply <planHash>`; `--plan-out` saves a replayable plan. |
| remote | `pr publish`, `pr sync` | The preview reads the platform; `--yes` or `--apply <planHash>` re-plans under a lock, writes the remote first, reads it back, then writes the local documents and the sync record. Never replayable from a saved plan (`REMOTE_PLAN_NOT_PORTABLE`). |

| Exit | Meaning |
| --- | --- |
| 0 | ok, planned, applied or unchanged |
| 1 | failed or blocked: validation, refused transition, lock, conflict, gate not passed |
| 2 | uncertain: a remote write whose outcome is unknown, or a local record that failed after a remote write (`data.uncertain: true`) |
| 130 | cancelled |

## JSON results

Every command prints one versioned envelope with `--json`:
`{ "protocolVersion": 1, "command", "status", "data", "diagnostics" }`. The `data`
shapes, abbreviated:

```text
increment list   { folder, increments: [{ id, title, status, size, owner, path, branch,
                   pullRequests: [{ id, path, status, kind, head, base, number?, url? }],
                   issues: [{ id, status }], problems }], drift: [] }
increment show   { increment: { …frontmatter, heading, sections: [{ name, line, words }], scope: { in, out },
                   acceptance: [{ id, checked, text, evidence, line }], path, links: [{ target, status }],
                   pullRequests: [] }, validation: { problems: [{ code, message, line? }] },
                   readiness, transitions: [], next }
increment check  { gate, status, handoff, base: { ref, sha }, scope: { kind, pullRequest, base, head },
                   rules: [{ id, title, severity, status, message, hint?, details? }],
                   refinement?: { skills, newHandoff, questions: [{ rule, title, questions }] },
                   generated: { paths, … }, source: "definition-of-ready" | "definition-of-done" }
                 or, without the gates: { gate, status, handoff, source: "structural", problems }
validate         { documents: [{ kind, id, path, problems }], drift, problems }
pr list          { folder, pullRequests: [{ id, path, status, kind, head, base, number?, url?, title,
                   increment, tasks: { total, done } }] }

                   binding, path }, remote: "not-contacted", validation, next }

                   edits: [{ section, action, itemId? }], kind?, head?, base?, delivers?, created?,
                   branch?: { status, name, start, commit, switch, fetch }, warnings }, conflicts,
                   changes: [{ path, status, beforeHash, afterHash }], steps?: [{ kind: "git-branch", … }],
                   applied? }
pr publish       { planHash, mode: "preview" | "applied", pullRequest: { id, path, increment },
                   remote: { platform, repository, head, base, action: "create" | "adopt", existing,
                   headExists, needsPush, steps, readiness, number?, url?, state? },
                   rendered: { title, bodyChars, bodySha256, limit }, changes, increment: { statusBefore,
                   statusAfter }, warnings, push?, pushed?, applied? }

                   merge: { title, regions, tasks: { pulled, pushed, imported, restored, removed },
```

The human output of the same commands is a view of this result; `--json` is the
authority for scripts and agents.
