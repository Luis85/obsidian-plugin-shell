# Declarative actions and native note generation

## Authoring workflow

Open a Page or Component element form. Inputs expose a subtype and required flag; selects take a bounded list of JSON `label`/`value` options. Reusable instances expose one multi-select per declared slot; select unassigned root elements to render inside that slot. Interaction forms expose a source operation or component emission plus a data-only payload mapping. Saving new semantics upgrades `detailDesigns.schema` to 2 through the existing guarded transaction. Old schema-1 designs remain valid and unchanged.

Input kinds are `text`, `textarea`, `number`, `checkbox`, `date`, `datetime-local`, `select`, `json-file`, `json-editor` and `markdown-editor`. Numbers remain numbers and checkboxes remain booleans. Zero, false, empty text and a missing value are different states. Invalid raw input stays visible and blocks action dispatch. JSON/Markdown editors are plain-text controls; JSON input and selected local JSON files are bounded and parsed as data. No HTML, expressions, plugin code, or network request is executed while authoring or generating.

Slot assignments map declared slot names to ordered root node IDs. Roots cannot be claimed by two slots, and assignments cannot form recursive containment. Assigned roots disappear from their former outer rendering location, so content renders once. Hidden ancestors and the receiving slot's declared states apply to assigned content. Duplication remaps owned slot subtrees and internal draft mappings. Deleting an input used by a surviving action is blocked until the mapping is repaired.

## Payload contract

A detail edge can declare one source action:

```json
{
  "kind": "source",
  "sourceId": "ds-source-900",
  "operationId": "ds-operation-902",
  "input": {
    "kind": "object",
    "fields": {
      "requestId": {"kind": "prop", "name": "requestId"},
      "values": {
        "kind": "object",
        "fields": {
          "title": {"kind": "draft", "nodeId": "detail-node-101"}
        }
      }
    }
  }
}
```

The `requestId` prop must be declared by the owning reusable component; a page without that prop must supply another declared source, draft or event value. Issue one stable unique request ID per create intent and reuse it only to retry that same intent. A fixed literal ID is appropriate for a bounded test, not for repeated user-created records. The generator does not invent a business idempotency strategy.

Mappings support `none`, `value`, `draft`, `prop`, `event`, `source`, and nested `object`. A source mapping specifies `sourceId`, `operationId`, and `field`; paths select own data properties only. Required/missing references, unsupported types, prototype keys and oversized/cyclic values are rejected. Input/change events yield parsed control values, not DOM Event objects. Component actions can use `{"kind":"emit","event":"select","payload":{"kind":"value","value":"record-id"}}` for a declared primitive event. Source calls still pass through generated input/output validators, application services and actual per-view Pinia stores. An emitted event or dispatched action is not proof of its business outcome.

## Native note operations

In a vault source operation, the advanced native declaration is:

```json
{"kind":"note","entity":"er-entity-900","operation":"create"}
```

It lives in the operation's optional `implementation` property. `resource` must match the entity's nonempty declared folder exactly. The entity needs a required string `title`, portable frontmatter keys, and supported scalar or string-list fields. Nested objects, mixed numeric lists, custom codecs and conflicts with retained example entities are rejected instead of silently dropping data. Existing no-input read operations whose output is an entity collection and whose resource matches its folder compile to native repository lists as well.

The exact wire shapes are generated by `noteWireSchemas` in `scripts/companion/compiler/note-contracts.ts` and demonstrated by `tests/fixtures/generator-boundaries.mjs`:

| Operation | Input | Output |
| --- | --- | --- |
| list | none | array of snapshots |
| create | `{values, requestId}` | snapshot |
| update | `{id, revision, values}` | snapshot |
| delete | `{id, revision}` | none |

A snapshot is `{record, revision}`. `record` matches the complete declared entity schema, including `id` and literal `type`. `values` contains every declared entity property other than `id` and `type`, with the original required flags and no additional properties. Top-level operation objects allow only the shown keys. `revision` is an integer; `id` and `requestId` are strings. The generator checks the exact schemas before writing a project, so an incompatible declared output cannot be discovered only after a mutation.

Generated adapters receive the one existing shell repository registry. Real NoteRepository and DocumentCreationService own Markdown encoding, frontmatter, path containment, idempotency, events and stale-write checks. Pinia never becomes a second persistence owner. Runtime leases retain real read snapshots; an invented revision cannot update/delete a note. Changes in storage after the read fail the canonical snapshot check. Update/delete use the existing cancellation permit. Cancellation before a create prevents it from starting; once canonical creation starts, cancellation does not promise to roll back or undo a committed note. A failed/uncertain write is not retried automatically.

## Verification and limits

`npm run verify:project` checks the generated build, Vue/TypeScript and generated tests. Native note tests use the real repository/Markdown codec and an in-memory storage port to verify all-field round trips, stale edits, preserved unrelated Markdown, idempotency and disposal. A registry integration test composes generated repositories with retained framework features. These are not tests inside native Obsidian.

The qualification command runs separately against the unmodified companion export and a synthetic design that declares the new semantics. PRD prose still produces explicit acceptance TODOs. Full visual editor conversion, custom API/database/auth integrations, domain-specific business rules, semantic relationship enforcement and native host acceptance remain separate work. Design System generation is integrated from PR #5 and remains plugin-scoped; no global host style override is introduced.
